## 呈現邏輯與修改邊界
1. loop → update 固定步進 → render；視覺有 CSS 時間、FR 繪圖幀、G.f／f.t 模擬時間三套來源。改節奏前先辨識，不能以畫面幀任意改技能時長。
2. DOM/CSS 選單與 Canvas HUD 分開繪製。Canvas 為800×450邏輯座標，DPR與畫質另縮放；hudClick將游標映射回邏輯座標。重排自動戰鬥按鈕必須同步HUDA。
3. drawChibi 同時用於戰鬥、選角、美容院、建立角色。預覽暫時切換全域 X；修改需驗證所有入口並恢復 context 狀態。
4. KF/poseOf/animate 處理姿勢，stepP/startAtk等處理狀態與攻擊。美術動作不能擅改攻速、判定、無敵、MP與冷卻。
5. render 先背景／色罩、招式預警、按 z 排序的物件，再技能／投射物／特效、前景提示、HUD。預警可能被後畫特效遮住；優化必須檢查圖層。
6. GQ影響DPR、粒子比例、FXCAP（180/360/620）與部分光暈；低畫質仍需看得懂危險區、稀有物、冷卻與命中。
7. itemIconC、glowSpr等有快取。換色／造型後須檢查cache key及失效；itemIconC的anc部分目前只區分有無遠古，不區分遠古系列，需要細分圖示時應一併調整。
8. 裝備／美容外觀依賴存檔；連線使用快照與訪客插值。僅換繪圖可較獨立，新增外觀欄位需存檔遷移與雙端相容性檢查。
9. 結算與轉蛋演出連結實際獎勵與計時器；跳過／重抽／關閉流程須驗證不重複發獎或卡住。
10. 實際render的sx=sy=0：雖仍有G.shake數值，不代表戰鬥目前真的震動。
